# Engineering Log

A running record of real changes to Sentinel — what was built, why, and any trade-offs made along the way. This isn't a changelog of every commit; it's for the changes worth being able to explain in an interview. Each entry should be short enough to write in five minutes, right after the work, while the reasoning is still fresh.

Template for each entry:

```
## YYYY-MM-DD — Short title

**What changed:** One or two sentences.

**Why:** The actual reasoning — what problem this solves, what it was before.

**Trade-offs / what I'd do differently at scale:** Optional but valuable — shows judgment, not just output.
```

## 2026-08-23 — Real GitHub adapter

**What changed:** Added `RealGitHubAdapter`, a GitHub REST API-backed implementation of the existing `GitHubAdapter` Protocol, authenticated with a read-only PAT (`GITHUB_TOKEN`/`GITHUB_REPO`, same opt-in pattern as `ANTHROPIC_API_KEY`). Wired it into `adapters/factory.py` so `SENTINEL_USE_MOCKS=false` now actually does something for GitHub instead of unconditionally raising `NotImplementedError` — it builds the real adapter if credentials are present, or raises a specific error naming exactly which env vars are missing if not. Metrics, runbooks, and Slack still have no real adapter, so they stay mocked in both modes; that's a deliberate, honest gap, not an oversight. Added 10 new offline tests (`httpx.MockTransport`, no real network calls) covering commit/deploy parsing, service tagging, 404/error handling, and the factory's branching logic. Full suite: 28 → 38 passing, no regressions.

**Why:** This was the top item on the roadmap and the prerequisite for making "root-cause commit identification" an honest claim rather than one running entirely against fixture JSON. It's also the one piece the rest of the correlation pipeline (`pipeline/correlate.py`) actually depends on for real signal — the scoring logic was already real, it just had nothing but mock data to score.

**Trade-offs / what I'd do differently at scale:** The adapter fetches full commit detail (`/commits/{sha}`) for every summary returned by the list endpoint to get accurate `additions`/`deletions`/`files_changed` — that's an N+1 call pattern against a rate-limited API. Fine at `limit=25` for a portfolio-scale demo; at real scale I'd either cache commit details or only fetch the detail for the top-N candidates after an initial cheap scoring pass on the summary data. I also collapsed "service" to a 1:1 mapping with the configured repo (every commit/deploy from `GITHUB_REPO` is tagged with the repo's short name) rather than inferring per-file service ownership — that matches how this adapter is actually scoped (one repo = one service) but wouldn't hold up against a monorepo without a real service-ownership mapping.

## 2026-08-23 — GitHub Actions CI

**What changed:** Added `.github/workflows/ci.yml`: runs `ruff check .` and `pytest -q` on every push to `main` and every PR, Python 3.12, installed via `pip install -e ".[dev]"`. Pinned ruff to a conservative rule set (`F`, `E4`, `E7`, `E9` — pyflakes plus real pycodestyle errors, not line-length/formatting opinions the codebase never adopted) rather than accepting its much broader modern defaults, which would have flagged ~20 pre-existing style choices unrelated to correctness. Fixed the two real issues that selection did surface (a dead variable in the metrics mock, an unused import in a test). Verified green on GitHub after push, not just locally.

**Why:** Roadmap item 2, and a prerequisite for trusting any future PR without manually re-running the suite. Setting up lint also surfaced a real latent bug: several tests called `get_settings()`/`get_adapters()` with no override, so a developer's local `.env` (in this case, `SENTINEL_USE_MOCKS=false` left over from the GitHub adapter smoke test) silently changed what the suite exercised — 5 tests failed hitting the live API instead of mocks. Fixed by having every test fixture build `Settings(_env_file=None)` explicitly, so the suite is hermetic regardless of local `.env` contents. This would have made CI itself unreliable in a subtler way (CI has no `.env`, so it wouldn't have hit this specific failure — but the underlying fragility, tests silently depending on ambient state instead of being self-contained, was a real correctness gap worth closing while I had it in front of me).

**Trade-offs / what I'd do differently at scale:** No dependency caching between runs (`actions/setup-python`'s pip cache isn't enabled) and no matrix across Python versions — both fine for a single-maintainer portfolio project with a small dependency set and a `requires-python >=3.10` floor that isn't being actively tested. I chose a narrow, explicit lint rule set over ruff's fuller defaults specifically to avoid a large drive-by reformatting diff in a CI-setup commit; the trade-off is that real modernization opportunities (e.g. `Optional[X]` → `X | None`) stay unflagged until someone deliberately opts into them.

## 2026-08-23 — Webhook authentication

**What changed:** Added `sentinel/api/auth.py`: a FastAPI dependency that requires a valid `X-Sentinel-Signature-256` header (HMAC-SHA256 over the raw request body, the same scheme GitHub itself uses for its webhooks) once `SENTINEL_WEBHOOK_SECRET` is set. Blank secret (the default) disables verification entirely, matching every other real-integration credential's offline-friendly default in this project. Wired it onto both `/webhook/alert` and `/webhook/resolve` as a route dependency. Added 8 tests: full coverage of the auth dependency against an isolated dummy app (disabled-by-default, missing header, wrong signature, signature computed with the wrong secret, tampered body, valid signature), plus two integration checks confirming it's actually wired onto the real endpoints. Full suite: 38 → 46 passing, no regressions.

**Why:** Roadmap item 3. `/webhook/alert` is a public-facing ingestion endpoint that triggers a real pipeline run (LLM calls, Slack posts, GitHub API calls once real credentials are configured) — right now anyone who finds the URL can POST arbitrary alerts and make Sentinel act on them. HMAC-over-the-body is the standard shape for this problem (GitHub, Stripe, and most webhook providers all use some variant), so implementing it this way means the same mental model transfers if a real upstream (GitHub webhooks, PagerDuty, etc.) is added as a source later.

I also corrected the roadmap's own note on this item, which said to do this "alongside a real GitHub webhook, not the PAT-only version." That doesn't describe anything on this roadmap — `/webhook/alert` is Sentinel's own alert intake, not a GitHub webhook receiver, and item 1 deliberately chose PAT-polling. Left a note in `docs/ROADMAP.md` explaining the correction so it doesn't cause confusion again.

**Trade-offs / what I'd do differently at scale:** Hit one real FastAPI dependency-injection gotcha worth remembering: the auth dependency needs `Settings` via `Annotated[Settings, Depends(get_settings)]`, not a plain function parameter with a default — FastAPI otherwise treats any bare Pydantic-model parameter as a second request-body field to embed, which silently turned every request into a 422 regardless of signature. Caught it by manually exercising the endpoint with `TestClient` before writing the formal tests, not by the tests themselves (they were written after the fix). The signature only covers the request body, not headers/method/path, so this doesn't protect against replay attacks (same signed body resent later) — fine for a portfolio project's threat model, but at real scale I'd add a timestamp header into the signed payload and reject requests outside a short window, the way Stripe and Slack do it.

## 2026-08-23 — SQLite persistence

**What changed:** Replaced the dict-backed `IncidentStore` with a SQLite-backed one, same file, same public interface. Incidents are stored as one JSON blob per row (`Incident.model_dump_json()`/`model_validate_json()`), keyed by id, with `created_at` indexed for list ordering — not a normalized per-field schema, since the pipeline only ever needs whole-incident reads/writes and the Incident shape already grows as pipeline stages get added. A single `sqlite3` connection guarded by a `threading.Lock` handles concurrent access. `IncidentStore()` still defaults to an in-memory database, so every existing call site (`scripts/simulate.py`, the tests) keeps getting a fresh, isolated store with zero code changes; the process-wide `get_store()` singleton now persists to `SENTINEL_DB_PATH` (default `sentinel.db` at the repo root, already gitignored — the `.gitignore` had `*.db` in it well before this session, so this was clearly the intended design). Added 8 new tests covering idempotency, save-persists-mutations, resolve's mutation actually being written (not just returned), list ordering, in-memory isolation between instances, and real on-disk persistence verified across two separate `IncidentStore` instances pointed at the same file via `tmp_path`. Full suite: 46 → 54 passing, no regressions.

**Why:** Roadmap item 4. The in-memory store meant every incident vanished on process restart — fine for a demo script, not defensible as "persistence" on a resume. Keeping the same public interface (`create_from_alert`/`get`/`save`/`list`/`resolve`) meant the orchestrator and API layer needed zero changes; the whole point of isolating the store behind its own module in the first place.

Also had to fix one test that was asserting an implementation detail rather than a real contract: `test_incident_is_persisted_and_listable` checked `store.get(id) is incident` (object identity), which only held because the old store kept the exact same Python object by reference in a dict. A SQLite-backed store correctly returns a new, equal-but-distinct object on every `get()` (it round-trips through JSON), so I changed the assertion to `==`. That's the right invariant for a persisted store to guarantee — identity was never a real promise of the `IncidentStore` interface, just an accident of the old implementation.

**Trade-offs / what I'd do differently at scale:** A single connection serialized by one lock means writes are fully serialized process-wide — fine for a demo's request volume, but it's a throughput ceiling at real scale; I'd move to a connection pool (or `aiosqlite`/async driver, or graduate to Postgres) once concurrent writers actually contend. Storing the whole incident as a JSON blob instead of a normalized schema means you can't efficiently query "all SEV1 incidents" or "incidents touching service X" without loading and deserializing every row — acceptable for a store with no query/filter endpoints today, but the first thing I'd change if `/incidents` grew a filter parameter. Also caught and fixed a real footgun in `.env.example` while documenting this: `SENTINEL_DB_PATH=` (blank) doesn't mean "use the default" the way blank credential fields do — it coerces to `Path("")` which resolves to `"."`, the current directory. Left it commented out with a sample value instead of shipping a live blank line that would silently misconfigure the database location.

## 2026-08-23 — Async pipeline execution

**What changed:** Both `/webhook/alert` and `/webhook/resolve` now return `202 Accepted` immediately with the incident as it exists at that moment, and run the actual work — stages 1–4 (`Orchestrator.enrich_incident`) or stage 5 (`Orchestrator.generate_and_save_postmortem`) — via FastAPI `BackgroundTasks` afterward. Callers poll `GET /incidents/{id}` to see suspects/runbook/impact/brief or the postmortem land. Split `Orchestrator.handle_alert`/`resolve_incident` into paired methods (`create_incident`+`enrich_incident`, `mark_resolved`+`generate_and_save_postmortem`); the original two are now thin compositions of the split methods and keep their exact prior synchronous, fully-blocking contract, so `scripts/simulate.py` and every existing test needed zero changes. Along the way, switched `Orchestrator` construction and the `GET` endpoints' store access to real FastAPI DI (`Depends(get_orchestrator)`, `Depends(get_store)`) instead of calling the global singletons directly inside handler bodies. Added 10 new tests (5 at the orchestrator level: `create_incident` runs no stages, `enrich_incident` completes and persists them, `handle_alert` is provably equal to the two composed, `mark_resolved` doesn't generate a postmortem, `generate_and_save_postmortem` does and persists it; 5 end-to-end via `TestClient` against the real endpoints: 202 + pre-enrichment body on POST, full results on a subsequent GET, for both flows, plus the 404-unknown-incident case still working). Full suite: 54 → 64 passing, no regressions.

**Why:** Roadmap item 5. Before this, `POST /webhook/alert` held the HTTP connection open for the full pipeline — commit correlation, an LLM call for the brief, a Slack post — before responding. That's a bad shape for a webhook receiver (most monitoring systems that fire alerts expect a fast ack and will retry or give up on slow responses) and made "real-time incident response system" an overstatement; the system was real-time in the sense that it *reacted* to alerts, but every caller was blocked for the full pipeline latency.

**Trade-offs / what I'd do differently at scale:** Found a real bug while manually verifying the new flow end-to-end with `TestClient` before writing any formal tests (same habit as the webhook-auth session): a test-injected `Orchestrator` built with its own isolated `IncidentStore()` and the `GET` endpoints' `get_store()` singleton were two different stores, so `GET /incidents/{id}` 404'd even though the background task had completed and saved successfully. That's what pushed the `Depends(get_store)` refactor — it wasn't optional polish, the endpoints were untestable in isolation without it, which is itself a sign the original direct-singleton-call design was a testability gap even before this session. FastAPI's `BackgroundTasks` runs one job per request on the same process, in a thread pool for a sync callable — fine here since there's no retry, no persistence of "a background job is in flight," and no way to know a job failed short of reading server logs. At real scale (or the moment two pipeline stages both need to call slow external APIs and one fails independently), I'd move to a real task queue (Celery, RQ, or an outbox-pattern table) with retries and observable job status, and probably expose incident status as `open` / `enriching` / `enriched` / `resolving` / `resolved` explicitly rather than inferring progress from which timeline events exist.

## 2026-08-23 — Embedding-based runbook retrieval

**What changed:** Added `sentinel/pipeline/embeddings.py`: embeds the alert text and each runbook's text with a local sentence-transformer model (`all-MiniLM-L6-v2` by default) and ranks by cosine similarity, as an alternative to the heuristic keyword/tag/service scorer already in `runbook.py`. `find_runbook()` dispatches between the two based on `SENTINEL_USE_EMBEDDINGS` (default `false` — heuristic scoring, byte-for-byte unchanged behavior). `sentence-transformers` (which pulls in `torch`) is a new optional `embeddings` extra in `pyproject.toml`, not a core dependency, and is imported lazily inside the module, not at import time — so the base install, CI, and every existing code path are completely unaffected whether or not it's ever installed. Added 6 tests, all built on a hand-picked deterministic fake `embed_fn` (cosine-similarity ranking across multiple runbooks, partial-vs-orthogonal-match ordering, the empty-list short circuit, and that `find_runbook()` correctly dispatches to each path) — none of them import `sentence-transformers` or touch a real model. Full suite: 64 → 70 passing, no regressions.

**Why:** Roadmap item 6, explicitly framed as "the genuinely AI engineering item on this list, not just called an API" — the rest of the pipeline is deterministic scoring/rule logic plus an LLM API wrapper; this is the one place a real local ML model with actual vector math lives, which is worth being able to talk through in an interview (why cosine similarity, why normalize embeddings, why this isn't a "call an API and hope" integration).

I deliberately did *not* make this the default or a CI-tested-with-a-real-model path. `sentence-transformers` pulls in `torch`, which is a large download (hundreds of MB to a few GB depending on platform) and the model itself downloads from Hugging Face on first use — adding that to the default install or to CI would make `pip install -e ".[dev]"` slow and `SENTINEL_USE_EMBEDDINGS=true` in a test run flaky/network-dependent, both of which contradict this project's whole "offline-friendly by default" design (every other real integration in this codebase follows the same shape: off by default, real and functional when explicitly opted into, never a CI dependency). The heuristic scorer isn't a placeholder being "upgraded away" here — for a 3-file runbook corpus it's arguably still the better choice; the embedding path exists to demonstrate the technique, not because keyword matching was inadequate.

**Trade-offs / what I'd do differently at scale:** The "vector store" here is genuinely just a Python list — embeddings are computed fresh on every call rather than precomputed/cached/indexed, which is fine for 3 runbooks and would be the first thing to fix (precompute + cache runbook embeddings, only embed the alert per-request) before this could handle a real runbook library of hundreds of documents. No exact "no match" case the way the heuristic has one: general sentence embeddings rarely produce exactly-zero or negative cosine similarity for unrelated short texts the way exact keyword overlap naturally does, so I kept the threshold at "non-positive" rather than inventing an untested similarity cutoff — I have not run this against the real model (no time/dependency budget in this session), so I did not want to hardcode a magic number I couldn't justify. Whoever enables this for real should sanity-check that threshold against real alert/runbook pairs before trusting the None case.

**To actually try the real model:** `pip install -e ".[embeddings]"` (downloads torch), set `SENTINEL_USE_EMBEDDINGS=true` in `.env`, then call `find_runbook()` (e.g. via the simulate script or a real webhook alert) — the first call downloads the model from Hugging Face and caches it locally; subsequent calls are fast.

## 2026-08-23 — Docker support

**What changed:** Added a `Dockerfile` (`python:3.12-slim`, non-root user, `HEALTHCHECK` against `/healthz`, `EXPOSE 8000`, `CMD` runs `uvicorn sentinel.api.main:app`) and `docker-compose.yml` (single service, a named volume so the SQLite database survives `docker compose down`/rebuilds, env vars pass through from a local `.env` with mocked-mode defaults so `docker compose up` works with zero setup). Added a `.dockerignore`. `sentence-transformers`/`torch` (the `embeddings` extra from item 6) is deliberately not installed in the image, keeping it small and consistent with that feature being off by default everywhere.

**Why:** Roadmap item 7 — makes "Docker" on the resume an actually-true claim instead of aspirational, and it's the natural way to hand someone (an interviewer, yourself on a different machine) a single command that runs the real thing.

**A real limitation, stated plainly:** Docker isn't installed in the environment I did this session's work in, so I could not run `docker build`/`docker run` myself to verify the Dockerfile actually works. What I did instead: (1) ran the exact `CMD` (`uvicorn sentinel.api.main:app --host 0.0.0.0 --port 8000`) directly on the host and confirmed `/healthz` and `/incidents` respond correctly, which validates the app-boot half of the image; (2) added a `docker` job to `.github/workflows/ci.yml` that runs on GitHub's Ubuntu runners (which do have Docker preinstalled) — it builds the image for real, runs the container, and POSTs a real alert through `/webhook/alert`, then asserts `GET /incidents/{id}` shows a populated (non-null) `brief` object, proving the background-enrichment pipeline actually completed inside the container, not just that the process started. That job passed. This is genuine automated verification, not a claim I couldn't back up — but it's still worth being upfront that I never personally ran `docker compose up` and looked at it, and you should before calling this done for real.

One real design decision worth being able to explain: the Dockerfile uses `pip install -e .` (editable), not a normal `pip install .`. `sentinel/config.py` computes `runbooks_dir`/`fixtures_dir`/`db_path` defaults as paths relative to `sentinel/config.py`'s own `__file__` (two parents up). Under a normal install, `pip` copies the `sentinel` package into `site-packages`, so that relative-path computation would silently resolve to somewhere under `site-packages` instead of `/app` — the container would boot fine and then fail to find `runbooks/`/`fixtures/` or write its database in the wrong place, with no obvious error pointing at the real cause. An editable install keeps `__file__` pointing at the actual `/app/sentinel/config.py`, so the existing path-resolution logic just works, with zero changes to application code.

**Trade-offs / what I'd do differently at scale:** The real fix for the `__file__`-relative-path fragility I just described isn't "always use an editable install forever" — it's making `runbooks_dir`/`fixtures_dir` properly env-configurable the same way I already made `db_path` in item 4, so the app doesn't depend on install mode at all. Didn't do that tonight because it touches production config code beyond "add a Dockerfile," and the editable-install workaround is correct and low-risk. Also: no multi-stage build (there's nothing here that needs a separate build stage — no compiled extensions, no frontend build step), no non-`amd64` architecture testing, and the image isn't pinned to a specific `python:3.12-slim` digest, so a base-image update could change behavior under you without a corresponding commit here.

## 2026-08-23 — Real Slack adapter

**What changed:** Added `RealSlackAdapter` (`sentinel/adapters/slack_real.py`), the real counterpart to `MockSlackAdapter`, using Slack's Incoming Webhooks feature: POST a JSON body to a webhook URL, get back `"ok"`. Wired into the factory as its own independent toggle — `SLACK_WEBHOOK_URL` alone makes Slack posts real, whether or not `SENTINEL_USE_MOCKS`/GitHub credentials are set, unlike GitHub which is still gated by the combined `use_mocks` switch. Added 3 tests for the adapter (required URL, successful POST sends the right body and returns an id, error response raises `SlackAPIError`) and 3 for the factory wiring (stays mocked without a URL, becomes real with one, independent of GitHub's settings) — all offline via `httpx.MockTransport`. While adding the factory tests, noticed and fixed a pre-existing gap: `test_factory.py`'s `Settings(...)` calls only overrode the fields each test cared about, so unrelated fields could silently pick up a developer's real `.env` values (same class of bug fixed in the CI session, just missed in this one file). Hardened every call in that file with `_env_file=None`. Full suite: 70 → 76 passing, no regressions.

**Why:** Roadmap item 8, but built as real Slack rather than the roadmap's literal Discord suggestion, per direct request mid-session ("can we still have slack without discord?"). That turned out to be a better outcome, not a compromise: the roadmap's stated reason for preferring Discord was that full Slack integration (bot token, OAuth scopes, workspace app-review) is disproportionate friction — true for the Web API, but Incoming Webhooks sidestep exactly that friction (create a webhook URL in your own workspace, no review process) while keeping the codebase's existing `SlackAdapter` Protocol, naming, and mental model intact instead of introducing a second, parallel notification concept just for this one item.

**Trade-offs / what I'd do differently at scale:** An Incoming Webhook is bound to one fixed channel, set when you create it in Slack's UI — the adapter still accepts a `channel` argument (Protocol compatibility with `MockSlackAdapter`, which does route by channel), but it's not actually authoritative for the real adapter; posting to multiple channels for real would mean either provisioning one webhook URL per channel or switching to the full `chat.postMessage` Web API with a bot token, at the cost of the setup friction this approach was chosen to avoid. Also, Incoming Webhooks don't return a real message timestamp/id the way `chat.postMessage` does (just the literal string `"ok"`), so `Incident.slack_ts` gets a locally synthesized id instead of a real Slack message reference you could deep-link to — fine for "did this post land," not fine if a future feature needs to edit or thread-reply to that exact message.

**To actually test this live:** create a Slack Incoming Webhook (api.slack.com/apps → your app → Incoming Webhooks → Add New Webhook to Workspace, or create a new app first if you don't have one), copy the URL into `SLACK_WEBHOOK_URL` in `.env`, then trigger any alert (e.g. via `/webhook/alert` or the simulate script) — the brief posted at stage 4 will land in the real channel you picked. No `SENTINEL_USE_MOCKS`/GitHub setup required for this specifically.
